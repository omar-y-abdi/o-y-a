## Main flow map

- **Edit and Save:** inspector/editor changes pass through `change()` into `Draft.change()` (`src/cms/client/app.mjs:80`; `draft.mjs:40-51`). `save()` captures a stable owner and request, persists a local backup before the API call, acknowledges the submitted snapshot, and permits one follow-up save for later edits (`app.mjs:460-487`). Non-definitive failures retain the pending request in `Draft.rejectSave()` (`draft.mjs:29-38`); the status and error dialog preserve export/recovery paths (`app.mjs:494-498`).
- **Undo/redo and reload recovery:** the studio action calls `Draft.undo/redo` and reconstructs the relevant page/card/email view (`app.mjs:648-658`). Backup writes are scheduled from current draft snapshots; recovery validates the record and base revision, checks the active owner/snapshot/version again before install, persists the new independent copy, then discards the inactive record (`backups.mjs:25-37,44-67`). `beforeunload` protects dirty site/SVG drafts (`app.mjs:757`). Frozen email sends have a separate session-storage path; ordinary compose state is intentionally not website draft data (`email.mjs:50-78,125-130,232-248`).
- **Conflict/reconcile:** the client captures draft owner, object snapshot, and version before fetching current state, checks the captured tuple after each await/decision, merges against the prior saved base, and requires a choice when conflicts remain (`app.mjs:510-523,546-550`). The path is guarded against same-tab edits while the network request or choice is pending.
- **Frame ownership:** `composeEditorPage()` puts page main content into the shared frame (`frame-project.mjs:8-19`). `frameSnapshot()` loads frame CSS first and tags frame/page rules separately, refusing duplicate selectors (`frame-project.mjs:21-36`); later snapshot and client choice code preserve the ownership and conflict distinction. Editor boundary and resize behavior are covered by changed CMS editor/frame specs as static contract evidence.
- **Mejl compose/send:** template edits enter `Draft`; compose edits go to module memory. Ambiguous sends freeze request ID and exact body in session storage, disable fields, and retry with that same body; definitive refusal paths unlock it (`email.mjs:50-78,101-123`, plus compose handlers). The panel warns that ordinary compose is not saved with the site (`email.mjs:232-248`).
- **Public copy/privacy:** public runtime text resolves from CMS preview data, then embedded JSON, then one shared `/data/runtime.json` request, retaining defaults on invalid/unavailable data (`src/client/copy.mjs:98-113,127-158`). Consent tracking requires analytics availability, an explicit `allow`, no session denial, and no GPC/DNT signal (`src/client/main.mjs:73-91`); preview suppresses the configuration request (`main.mjs:137-147`).
- **SKIFT page startup:** `scripts/build.mjs:27-43` builds an immutable app URL and rewrites the bootstrap import to it. ## Findings

### SP-01 — P2: a failed SKIFT bundle import leaves the game at an indefinite loading screen

**Proven behavior.** If the generated `app.js` request fails (or its module body rejects before `main.js` executes), the fire-and-forget dynamic import in `src/client/main.mjs:6-8` has no rejection handler. The import in `src/client/skift-bootstrap.mjs:3-4` is top-level awaited, so that rejection prevents the game entry module from running. The useful startup `try/catch` at `games/skift/src/main.js:74-98` only exists inside the app that failed to load. The game HTML starts with the Start button disabled and the status saying “building the workshop” (`games/skift/index.html:21,26`), so the game remains unusable with no visible explanation or reload action; only the browser error is reported, as the main-module comment says.

**Regression evidence and gap.** `tests/public-startup.spec.mjs:68-74` replaces the app with a successful empty JS body. The other shell tests likewise return successful game code. No changed test rejects the bootstrap/app request or asserts visible recovery.

**Fix and regression.** Catch bootstrap rejection at the shell/game boundary and set a visible localized game startup error with a reload action, while keeping the portfolio shell usable. Add a browser case where the immutable `app.js` request fails and assert the shell remains active and the game presents recovery instead of remaining in loading state. Commit `c2cf014` deliberately removed a 25-byte console-only catch to fit a reported 14,000-byte gzip cap (commit message reports 14,019 bytes with that catch and 13,990 without); do not simply re-add the old no-UI catch. The present bundle size and budget have not been measured in this review; keep or revalidate that constraint as part of the repair.

**Confidence.** High on the import/catch boundary and resulting disabled/loading UI; conditional on the game bundle or bootstrap request failing.

### SP-02 — P2: tablet navigation disappears when the public entry module fails

**Proven behavior.** At widths 761–1000, `src/styles/base.css:27` provides an expanded primary-nav fallback while `html:not(.js-ready)`. The newly added `base.css:30` overrides that fallback whenever `(scripting:enabled)`, hiding `.primary-nav` until `.js-ready` changes. The menu button has the `hidden` attribute in `src/templates/layout.mjs:42`; only `src/client/main.mjs:10-11` reveals it and removes `hidden`. If JavaScript is enabled but the public entry module cannot load or parse, neither nav path is available: the fallback links are hidden by CSS and the menu button remains hidden in HTML.

**Regression evidence and gap.** `tests/public-pages.spec.mjs:63-75` checks JavaScript-disabled fallback only at 390 and 1440 pixels. It does not cover a failed module load, nor the 761–1000 range for no-JS/failure behavior.

**Fix and regression.** Keep primary links visible until the entry module signals readiness, or otherwise gate the fallback on successful initialization rather than browser scripting capability. Add a 768px browser case that blocks the main module and verifies usable primary links remain visible. Preserve the existing successful tablet-menu test.

**Confidence.** High on the markup/CSS state transition; conditional on public entry-module load or parse failure in a browser evaluating the `scripting` media feature.

### SP-03 — P3, product semantics uncertain: Undo in Compose mutates unrelated site draft history

**Proven behavior.** `status()` enables global Undo whenever the project `Draft` has undo entries, without checking the email tab (`src/cms/client/app.mjs:36-41`). Compose fields are not project-draft changes: `email.mjs:107,119-123` routes Compose mutations into the in-memory compose object, while `app.mjs:658` always runs `draft.undo()` and then only refreshes the current email panel. Therefore, after a site/template draft edit followed by a Compose edit, clicking the studio Undo reverts the earlier project draft and leaves the Compose edit intact. The test suite verifies template undo (`tests/cms-email.spec.mjs:114-121`) but has no Compose/global-undo contract.

**Head-diff check.** The status condition is inherited, but PR14 adds the Compose view and its in-memory edit path, plus the `current.type === 'email'` undo/redo branch in `app.mjs:658`. The reported mismatch is specific to that new view and branch, not an assertion about the base studio's prior page/card Undo behavior.

**Why this is not a settled defect.** The Undo/Redo controls are workspace-level and may be intended to reach prior persistent website edits from any studio section. The code proves the action is unrelated to the visible compose fields; product intent is not specified in the source.

**Fix and regression.** Decide and pin the intended behavior before changing it. If Undo is contextual, disable it in Compose or provide Compose-local history; if it remains workspace-level, make its scope clear and test that contract. A regression should first create a site draft change, then edit Compose and exercise Undo, checking both draft and compose state.

**Confidence.** High on the state effect; medium on whether the effect violates intended behavior.
